# План работ по находкам DAP-пробы

Источник: `idea-dotnet-support/dap-probe/FINDINGS.md` — чёрный ящик по пакету `dotnet-debugger-dap` 0.1.0 (Windows и
Linux в Docker). Регрессионные тесты на все находки P1/P2 и L1–L5 уже написаны:
`tests/DotnetDebugger.Tests/FindingsTests.cs` (отлаживаемая сторона — `tests/TestApp/Findings.cs`, `tests/AsyncMainApp`).

Состояние на 2026-09-21, до исправлений: 43 случая; Windows — 40 красных / 3 зелёных, Linux (Docker) — 41 / 2.
Старый набор (289 тестов) зелёный.

Состояние на 2026-09-21, после этапов 0–6: 44 случая (добавлен явный двойник L2) зелёные на Windows и в Docker; полный
набор — 326 тестов. Что именно сделано и что решено иначе, чем задумывалось, — в разделе «Итоги» в конце.

Порядок работы: этапы сгруппированы по общим причинам; каждый этап переводит свою часть `FindingsTests` из красного в
зелёное. После каждого этапа — полный набор на Windows и `FindingsTests` в Docker.

## Этап 2. Сценарии, заметные каждому пользователю

- [x] **№1. Unhandled-исключения.** Останавливаться всегда; фильтр `unhandled` остаётся носителем условия по типу.
      Найти, почему на Windows код выхода 0 вместо `0xE0434352`. Возможно, поправить два старых теста с фильтрами.
- [x] **№2. Не-ASCII вывод на Windows.** Кодовая страница 65001 у отлаживаемого процесса (скрытая консоль +
      `SetConsoleOutputCP` либо декодирование по OEM — выбрать экспериментом). Проверить `runInTerminal` и stdin.
- [x] **№12. `stopAtEntry` с асинхронным `Main`.** Точка на `<Main>$` / `MoveNext`, а не на заглушке без точек следования.

## Этап 4. Большие данные и отзывчивость

Самая рискованная часть; дополнительно прогонять stress-тесты (`DOTNET_DEBUGGER_STRESS=1`).

- [x] **Лимит выдачи.** Не больше 10 000 детей на `variables` без пейджинга, плюс узел-примечание.
- [x] **Массовое чтение.** Примитивные массивы и `List<примитив>` — одним `ReadMemory`, без `ICorDebugValue` на элемент.
      Гипотеза по L1 (15 ГБ на миллион `int`): mscordbi держит каждый выданный объект до `Continue`. Сначала подтвердить
      замером памяти в Docker.
- [x] **Пейджинг `Dictionary`.** Проверять `start` против `Count`; переход к записи по индексу в `_entries`, без `Skip`.
- [x] **Отмена.** `cancel` и `disconnect` не ждут блокировку движка (сейчас `cancel` во время долгого `variables` вообще
      не получает ответа); флаг отмены, проверяемый в циклах перечисления; `CancelEvaluation` без блокировки.

## Итоги (2026-09-21)

Все этапы 0–6 выполнены; после каждого этапа прогонялись полный набор на Windows и соответствующая часть (в конце — весь
набор) в Docker.

Что получилось не так, как записано в плане:

- **№1, код выхода.** Причина нуля — не в адаптере: на Windows отладочный конвейер (mscordbi) — нативный отладчик процесса
  и после необработанного исключения завершает его сам, с кодом 0. Реальный код взять негде, поэтому при
  `DEBUG_EXCEPTION_UNHANDLED` и коде 0 адаптер сообщает `0xE0434352` — то, чем процесс завершился бы без отладчика.
  Старые тесты с фильтрами править не пришлось.
- **№2.** Выбрана кодовая страница 65001, а не декодирование по OEM (OEM теряет символы ещё в отлаживаемом процессе).
  У адаптера своя консоль, поэтому переключает короткий вспомогательный процесс: `dotnet-debugger --console-utf8 PID`
  (в колбэке старта рантайма, до управляемого кода). `runInTerminal` не затронут; в stdin режима `internalConsole`
  адаптер ничего не пишет, проверять нечего.
- **№16** (`--server`) в этапах не значился; отдельных правок не понадобилось: его тест зелёный.
- **№5 на Linux.** Второй отладчик отвергается в `RegisterForRuntimeStartup`; процесс убивал не он, а `disconnect` после
  неудачного attach (состояние attach оставалось наполовину выставленным). Attach теперь ждёт исхода колбэка и при
  неудаче возвращает состояние.
- **L1.** Гипотезу про 15 ГБ отдельно не измерял: после лимита в 10 000 и чтения примитивов одним `ReadMemory` запрос на
  миллион `int` обходится без `ICorDebugValue` на элемент (меньше секунды, Docker с `-m 6g` проходит). Массивы
  не-примитивов по-прежнему идут поэлементно — их спасают лимит и отмена.
- **№9.** Старый тест `SlowPropertiesBecomeLazyOnceTheBudgetIsSpent` ждал, что геттер на 1.5 с досчитается; при таймауте
  1 с он теперь `timed out`, остальные свойства — lazy. Тест поправлен. Раскрытие lazy-свойства — явное действие: 5 с.
- **L2.** Эксперимент в Docker: на .NET 8 сессию теряет и явное, и неявное вычисление `while (true) { }` (`Stop` не
  возвращается — ограничение рантайма до .NET 9); на .NET 10 оба пути восстанавливаются. Различия путей в адаптере нет.
  Оба теста на .NET < 9 под Unix проверяют честное сообщение и `terminate`; текст сообщения больше не называет «.NET 8»
  виновником при любом рантайме.
- **№3.** `stepIn` попадал в конструктор state machine (код пользователя без строк) и делал step-out, который возвращался
  только после всего kick-off метода. Теперь такой метод проходится step-in целиком. Остановка — на `{` метода, как и у
  синхронных методов; тест принимает `{` или первую инструкцию (как существующий тест для лямбд).
